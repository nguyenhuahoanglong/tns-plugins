# Portable Git Workflow

Use this skill for commits, pushes, branches, diffs, stashes, merges, and pull requests. It replaces bare `git commit` and hand-built PR commands so repository conventions, safety stops, and verification stay consistent.

## Invoke the installed CLI

Resolve `SKILL_ROOT` as the installed directory that contains this `SKILL.md`, then run Python from that directory; never depend on the current directory, a global function, or an external script path.

```text
python "<SKILL_ROOT>/scripts/git_skill.py" <command> --repository "<repo>" [options]
```

Run `doctor` before an unfamiliar repository and `context --brief` before a cold commit. The CLI emits one `=== HEADER ===` section and a `RESULT:` JSON record; use its zero/nonzero exit code as the operation result.

| Intent | CLI command |
|---|---|
| Prerequisites/readiness | `doctor` |
| Repository state | `context [--brief]` |
| Commit and push | `commit "type: summary" [--staged-only] [--no-prefix] [--dry-run]` |
| Create work branch | `branch "US/1234-description" [--preserve-dirty-default] [--dry-run]` |
| Merge default into current | `merge [--dry-run]` |
| Save work | `stash "WIP summary" [--include-untracked] [--dry-run]` |
| Preview/manage local branches or stashes | `branches [--delete-local-only] [--clear-stashes] --confirm [--dry-run]` |
| Preview/create PR | `pr [--target-branch "main"] [--description "..."] [--preview] [--dry-run]` |

## Interpret the full request

Treat a compound request such as “move my changes to a story branch, commit task 1907, then open a PR” as one autonomous plan. Discover branch, worktree, stash, and default-branch state before asking; ask only when two safe interpretations are equally plausible.

- A named missing work branch normally means create it from the resolved default branch.
- “Changes” with a clean worktree and a stash normally means reapply the relevant stash on the requested branch.
- When the current default branch is dirty and a new work branch is requested, use `branch --preserve-dirty-default`; it safely stashes including untracked work, creates the branch, and reapplies the stash. Stop for conflicts before committing.
- Use `--dry-run` or `pr --preview` to inspect any uncertain mutation first.

## Commit rules

When the session created the changes, stage only those files, then use `commit --staged-only`; do not absorb unrelated worktree changes. For a cold commit, run `context --brief` first and inspect the result before choosing the message.

Use this message shape:

```text
#<task-id> <type>: <imperative summary under 50 chars>

- What changed and why
```

Allowed types: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`. Do not add Co-Authored-By, Generated by, or AI/LLM credit lines.

The branch ID identifies the parent story; commit subjects identify the child task. If task `#1907` differs from branch `US/1878-...`, include `#1907` in the message and pass `--no-prefix`. If only one supplied ID could be either story or task, ask which role it has.

## PR rules and confirmations

Use `pr`, not raw Azure CLI PR creation. It resolves the target, extracts `#<task-id>` values from commit subjects, generates the title from the branch ID, selects the description, creates or previews the PR, and verifies/repairs metadata.

- A PR without task IDs stops unless `--allow-no-work-items` is explicitly requested.
- The story ID belongs in the title; task IDs from commits are the work-item links.
- `--description` overrides automatic description selection. Otherwise the CLI applies its supported description precedence.
- Use `--preview` before creation when metadata or target is uncertain.
- Branch deletion or stash clearing requires the matching action flag and `--confirm`; do not force-push, rewrite history, or delete remote branches without an explicit request.

For failure diagnosis and supported recovery, read `references/troubleshooting.md`. For PR behavior details, read `references/pr-workflow.md`.

## Verify Output

After a mutating workflow, run `scripts/verify_output.py --repository "<repo>" --result '<RESULT JSON>'` when deterministic postconditions matter. Add `--expected-file`, `--work-item`, or `--dry-run` only for applicable assertions; use failure output to stop and resolve the operation before claiming success.
